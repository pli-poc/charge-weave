# Ontology authoring service (under construction)

This package exposes a local modelling studio and MCP service for workspace reads, source-grounded inspection, bounded draft commands, validation, review and controlled publication. Semantic writes and class inspection use the repository's Python authoring adapter and shared generator parser. Reusing an existing global property name is deliberately rejected until impact-aware editing is supported. Some planned studio capabilities and end-to-end production publication evidence remain incomplete. Node 22.18 or newer and Python are required.

Set `CHARGEWEAVE_ALLOW_WORKSPACE_CREATE=1` to let reviewer sessions create a workspace through the studio or `ontology_workspace_create`. Supply a title and an exact, locally available commit SHA from the configured canonical repository. Its adapter sources must match the running service. The new workspace and its creation receipt are durable; retrying the same operation ID and request returns the original result. Both reviewer and draft credentials for this service can access all workspaces granted during its current run, up to 20. Grants reset on restart: configure `CHARGEWEAVE_WORKSPACE_ID` to select a saved workspace, or retry its original creation operation to grant it again. The service reads committed files and does not alter the checkout.

The loopback-only `GET /health` endpoint returns a minimal service name, version and liveness status without workspace data or credentials. It does not establish that validation or GitHub access is working. Host and browser-origin restrictions still apply.

The studio can download a bounded JSON evidence report for a completed job. The authenticated report identifies its workspace, baseline, revision, source digest, outcome, freshness and step statuses; it excludes raw check output. Freshness is evaluated when the report is downloaded, so a saved report cannot establish that a later draft is unchanged. It is not independent acceptance evidence or publication authorization.

Saved presentation views can be exported from the studio or read through `ontology_view_manifest_get`. The versioned JSON includes the saved view revision, layout, groups and notes, plus the workspace identity and source revision observed at export time. The observed source revision is not necessarily the revision when the view was saved. The manifest is presentation metadata and does not add ontology assertions; importing it is not yet supported.

`property.update` edits a declared field only when its expected range and cardinality match the current source. Shared property kinds and datatype ranges must remain consistent. The change review marks range changes and tightened cardinalities as potentially breaking; relaxed constraints also require review. These classifications are warnings, not evidence that existing data or consumers remain compatible. Add or update fixtures and run the appropriate checks before acceptance.

`ontology_changeset_apply` accepts an optional caller-supplied `rationale` for the whole command group. Successful new groups return a stable `commandGroupId` and record the reason and operation ID in activity history. Retrying the same request returns the same receipt; changing the reason requires a new operation ID. Historical entries created before this metadata was recorded may not have it.

`ontology_changeset_open` optionally records one change set for the entire current draft, including prior edits, with an intent and existing requirement references. Once opened, edits, undo and review must supply its ID. Accepted or rejected sets are locked until a reviewer calls `ontology_changeset_reopen`; reopening invalidates the previous acceptance even if source bytes have not changed. A pushed set is marked published and cannot be reopened. Existing workspaces that never opened an explicit set retain their legacy edit behavior. Starting a separate proposal after publication currently requires a new workspace from an appropriate reviewed baseline; automatic rebasing is not supported.

`ontology_constraint_templates` lists available templates. The structural templates require an existing optional object relationship or narrow a controlled-value set to a strict subset of at least two values. They compile through `model/domain.schema` and `tools/build.py`. A bounded valid-interval template is available for a new class with two new, declared single-valued date-time fields and an explicitly linked existing requirement. It writes a fixed rule to `model/audit-rules.json`, a deliberate violation to `tests/negative-cases.json`, positive and boundary cases to `tests/business-acceptance.json`, and synthetic all-class example values. These cases are explicitly marked template-derived. The independent audit requires separately authored positive and negative cases for each such rule; a reviewer can add separately chosen synthetic interval cases and expected outcomes in the studio or with `ontology_reviewer_interval_case_add`. The reviewer must assess their actual independence and business relevance; the system records their provenance but cannot establish either automatically. The template does not accept arbitrary SPARQL, create a requirement or establish business completeness. Existing version-four workspaces without all required source blobs must be recreated to use it.

From this directory, run `npm ci`, then create a workspace from the committed repository baseline with `npm start -- --create-workspace`. Record the returned workspace ID. The import reads `model/domain.schema` from Git at HEAD; uncommitted changes are not included. The default SQLite database is `workspaces.sqlite` in this directory; set `CHARGEWEAVE_WORKSPACE_DB` to change it and `CHARGEWEAVE_REPOSITORY` to select the local checkout. Run `npm run doctor` after configuring the workspace and token to check local prerequisites without printing credentials.

The local service receives a workspace store rather than a database connection, but the supplied `WorkspaceStore` implements its operations directly with SQLite. There is no interchangeable database adapter or supported database migration yet. A future hosted store must preserve transactional revision checks, receipts, event ordering, review evidence and publication recovery; changing the database path does not switch database engines.

Set `CHARGEWEAVE_WORKSPACE_ID` to the returned ID and `CHARGEWEAVE_DRAFT_TOKEN` to a long random secret of at least 32 bytes, then run `npm start`. The server listens only on `127.0.0.1:4317` (override the port with `CHARGEWEAVE_PORT`). MCP clients send the token in the `Authorization: Bearer` header. Do not commit or share the token. To permit a separate browser origin, explicitly set `CHARGEWEAVE_BROWSER_ORIGIN` to its exact origin; other origins are rejected. The draft token grants access to workspaces authorized in this service run, starting with the configured workspace; it does not grant reviewer or publisher operations.

To connect a local Codex CLI to the same running service, provide the same draft token in Codex's process environment and configure an HTTP MCP server. For example, in a private PowerShell session create a fresh token before starting the service:

```powershell
$env:CHARGEWEAVE_DRAFT_TOKEN = [Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
```

In Bash, the equivalent is `export CHARGEWEAVE_DRAFT_TOKEN="$(openssl rand -hex 32)"`. Start Codex from an environment containing the same value as the running service; generating another token in a second terminal will not authenticate it. Add the configuration explicitly in your own Codex environment:

```text
codex mcp add chargeweave --url http://127.0.0.1:4317/mcp --bearer-token-env-var CHARGEWEAVE_DRAFT_TOKEN
codex mcp list
```

Use the configured service port if different. The equivalent Codex configuration is `[mcp_servers.chargeweave]` with `url = "http://127.0.0.1:4317/mcp"` and `bearer_token_env_var = "CHARGEWEAVE_DRAFT_TOKEN"`; store only the environment variable name, never its value. See the [official Codex MCP documentation](https://developers.openai.com/codex/mcp). The service uses scoped draft authorization; Codex's own tool and filesystem permissions remain separate.

MCP clients can read versioned resource templates under `ontology://workspace/{workspaceId}/v1/`: `summary`, `entity/{entity}`, `changes`, and, when repository validation is configured, `evidence/{evidenceId}`. Entity identifiers may be local names or percent-encoded ChargeWeave development IRIs. These are bounded summaries; source patches and full job output remain available through the existing tools. Resource reads use the same session and workspace authorization as tool calls; knowing a URI does not grant access.

`ontology_workspace_get` returns workspace identity, revision, digest, change-set status, editable source names and event cursor without returning the entire ontology source or source manifest. Use search and entity tools for concepts and `ontology_changeset_diff` for the owning-source patches. Clients that previously read raw `schema`, `sourceManifest` or `sourceOverlays` from this tool must use those focused tools instead.

Application-level tool failures return `isError` and a structured `error` with a code, plain-language message and recovery guidance. Recognized conflicts, authorization failures, stale checks and uncertain publication outcomes have distinct codes. Unknown failures use a generic code without copying potentially sensitive exception text. MCP protocol and argument-schema errors remain separate.

For the local same-origin studio, install the locked dependencies in `client-runtime` and `website`, then run `npm run build --prefix ../website` from this directory. Set `CHARGEWEAVE_PAIRING_CODE` to a distinct random secret of at least 32 bytes before starting the service. Open the printed `/charge-weave-app/modelling/` URL and enter that code in **Pair local studio**. The code expires five minutes after service startup, is single-use, and is invalidated after five incorrect attempts. The resulting HttpOnly, SameSite=Strict session lasts up to eight hours, can access the workspaces authorized in this service run, and is removed by a successful **Disconnect** or service restart. The browser automatically resumes an existing session after a reload. Never put the code or bearer token in a URL or commit them. The service serves only supported files under `website/dist`; set `CHARGEWEAVE_WEB_DIST` to another built directory if needed.

For example, in a private PowerShell session, generate a fresh code with `$env:CHARGEWEAVE_PAIRING_CODE = [Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))`. Read that environment variable locally when entering the code. Generate the separate draft bearer credential independently. These local reviewer sessions can inspect review readiness and accept an eligible draft; branch push additionally requires explicit publisher configuration. Production identity and per-user grant management remain unimplemented.

An optional distinct `CHARGEWEAVE_REVIEWER_TOKEN` (at least 32 bytes) exposes review-readiness inspection in addition to draft operations for the service's authorized workspaces. It reports exact-digest checks and missing gates and can record a reviewer acceptance; branch push additionally requires explicit publisher configuration. This is an interim local credential, separate from browser pairing; per-user grant management is not implemented.

MCP request bodies are limited to 512 KiB. A slow event consumer is disconnected and should reconnect using its last event cursor. On a normal shutdown the service closes event streams and waits for active validation jobs before closing the database; an abrupt process termination leaves interrupted jobs for inspection on restart.

The authenticated `GET /events?workspaceId=<id>&after=<sequence>` endpoint streams committed changes as server-sent events. MCP mutations wake connected streams immediately after commit; periodic reads remain as a fallback for changes made by background work or other store users. Reconnect with the last event ID to replay later events. Each event includes the previous sequence for the same workspace; global sequence numbers may skip because other workspaces share the store. An unknown cursor returns 409 and requires a new snapshot. This feed is read-only; semantic changes still use MCP. Clients must deduplicate events and recover from a snapshot if they detect a gap or cannot apply a delta.

Run `npm test` to exercise the store and MCP transport. Workspace creation is available through the local command and, when explicitly enabled, the reviewer MCP tool. Review and controlled publication require the credentials and evidence described below.

Validation requires Python, Git, tar, and the pinned dependencies in `requirements.txt`. Set `CHARGEWEAVE_PYTHON` to the Python executable when it is not on PATH. Checks materialize the pinned baseline in a temporary directory and record the input revision and digest. The structural profile runs `tools/build.py`; the reference profile runs full generation, SHACL reference validation, business-rule negative fixtures, structural boundaries and focused business decisions. The audit profile runs generation and independent business traceability checks, including the independent cases required for template-derived rules. The acceptance profile also checks generated artifacts and runs the repository release gates individually; it requires Java and can take a long time. It requires a baseline exposing the supported release-gate catalogue. Passing these checks does not establish all independent acceptance evidence or authorize publication. Incomplete jobs are marked interrupted on restart.

Only one validation job may run per workspace. Retrying the same operation ID returns the original job; a different request is rejected while that job is active. Each completed step is retained in the bounded job output. Validation compares tracked model, benchmark, requirements, test and tool inputs against their pre-generation bytes, excluding the repository's known generated outputs. A substantive source rewrite fails the check rather than attributing the result to the earlier draft.

The isolated validation directory has its own Git metadata with `HEAD` set to the pinned baseline, so checks that record the commit can run without reading the user's checkout as their working tree. The draft schema remains an uncommitted overlay. The runner fetches the pinned commit only from the configured local repository and does not push or change that repository.

Completed jobs can be read through `ontology_evidence_get` using the job ID as the evidence ID. The response identifies the baseline commit, checked revision, source digest, scope, freshness and individual step outcomes. An interrupted or cancelled job is evidence of that outcome, not a passing validation. Passing acceptance jobs retain a bounded generated-file snapshot for publication preparation; other profiles provide summaries rather than a complete artifact archive. These records do not establish all required acceptance evidence.

Reference and release jobs also retain a bounded comparison of the generated-output catalogue after generation: baseline and candidate manifest hashes, file counts and exact-byte changes with per-file hashes. The result is tied to the job input and survives restart. Byte differences can include serialization or line-ending changes; the summary is not a generated patch or a substitute for acceptance evidence, and later failing checks do not become passing merely because generation succeeded.

`ontology_temporal_view_get` and the studio's temporal panel show the selected class's explicit time and window fields together with its policy from the pinned baseline or a version-four draft overlay. The policy file is checked against the workspace source manifest; a missing policy is shown as missing and is not inferred for a new class. Legacy workspaces without a complete source manifest cannot use this view. The displayed model revision and policy source are separate identities; the panel does not infer business valid-time or known-time semantics from field names.

`ontology_responsibility_view_get` and the responsibility panel match declared or inherited fields against the server's versioned, partial mapping of exact owner, property and target triples. Each binding retains its source location and mapping version. The mapping is presentation metadata, not a new ontology assertion or an exhaustive responsibility analysis; an empty result means only that no curated binding matched.

`ontology_change_impact_get` compares the current schema draft with the pinned baseline and indexes direct class/property references in the requirement and journey registers, audit rules and temporal queries, including a supported requirement draft overlay. It verifies each indexed source against the workspace manifest, limits the results, and reports omissions. Other queries, sources, dynamic dependencies and new requirements are outside this index, so the result is a review aid rather than complete impact or acceptance evidence.

Reviewer credentials can accept, request changes or reject with a reason against the exact baseline, revision and source digest. Acceptance requires a nonempty source change, a complete source manifest, and passing current structural, reference, independent-audit and acceptance jobs; the decision records the exact job IDs. A newer failed, cancelled or running job for a required profile blocks acceptance. Decisions and idempotency receipts survive restart; later edits make the decision stale. A rejection does not erase the draft. Draft credentials cannot call these reviewer tools. Passing checks and reviewer acceptance do not establish business completeness. Publication requires the separate explicit controls and checks described below.

Reviewer sessions can look up GitHub Actions runs for a full exact commit SHA using `ontology_github_commit_workflows` or the studio form. The lookup uses the configured publisher credential if present and otherwise uses the public API; it never returns the credential. Results distinguish pending, failed, incomplete and unavailable runs. They do not verify branch-protection required checks or deployment, and access or rate limits can make the lookup unavailable.

`ontology_github_required_checks` separately compares available main-branch status-check policy with check runs and commit statuses for that exact SHA. It reports unavailable policy, incomplete lists, ambiguous contexts and unsupported required workflows as unknown; skipped checks remain distinct from passing checks. Reading classic branch protection can require additional GitHub permissions, and the result does not establish merge eligibility, other branch rules or deployment.

After an exact draft has been accepted and its required checks are still current, `ontology_publication_prepare` starts an isolated preparation job. Validation first applies the repository's Git clean filters to generated files and runs the checks against those normalized bytes. Preparation restores the exact bytes retained from the passing acceptance job, checks their hashes and the source manifest, and stages only the expected source and generated files in a temporary checkout. Older acceptance jobs without a retained snapshot must be rerun. The job returns a file manifest and hashes; it does not create a commit, check the remote, or push. A changed draft, later review decision, stale checks, incomplete artifact evidence, or different staged bytes prevents preparation. Cancellation waits for the active build to finish before discarding the result. The temporary checkout is removed on completion.

Reviewers can save a local publication intent against a current accepted review and staged preview, including the proposed commit subject and description. The journal assigns an isolated branch name and persists intent and state across restarts; saving an intent creates no Git commit and performs no network write. A reviewer can then create a local commit using the repository's configured `user.name` and `user.email`. The server reconstructs and compares the saved staged manifest first and stores a recoverable Git bundle in the workspace database; it does not push. Commit creation cannot be cancelled once started.

To enable the explicit reviewer publication controls, set `CHARGEWEAVE_ALLOW_PUBLISH=1` and provide a distinct GitHub credential in `CHARGEWEAVE_GITHUB_TOKEN` with permission to write branches and pull requests in `pli-poc/charge-weave`. Keep this token private and out of the repository. The draft credential never receives the publication tools. The server checks that the configured origin is the canonical repository and that `main` still matches the reviewed baseline, then pushes without force to the journal's unique branch. A separate reviewer action opens a draft pull request after rechecking both branch heads. If a push or pull-request response is lost, the journal records an uncertain outcome; invoke the corresponding control again to inspect and reconcile the remote result. The server blocks semantic edits and review decisions during these network writes. Workflow lookup is available separately; branch-protection required checks and deployment are not verified.

Reviewer sessions can run `ontology_publication_preflight` to compare the pinned baseline with the current `main` head of the allowlisted ChargeWeave GitHub repository and inspect changed source paths and any fresh generated-byte summary. The check does not push, stage files, inspect branch protection or establish exact-commit CI status. For an advanced target, preflight fetches the pinned target and baseline into a disposable repository, checks ancestry and lists file-level overlaps; it reports a moved or unavailable target rather than assuming a result. Disjoint paths do not prove semantic compatibility, and any combined candidate needs review and validation. Preflight never authorizes publication. Tests use an isolated local bare remote and need no production credentials.

The draft comparison includes a unified patch for `model/domain.schema` alongside semantic summaries and before/after source. The patch is computed from the exact stored baseline and current draft; other editable source-owner patches are also shown; generated artifacts are summarized separately.

Workspaces created by the local bootstrap use digest version 4: a SHA-256 identity over the adapter version, immutable baseline commit and a path-sorted SHA-256 manifest of tracked model, benchmark, requirements, test and tool inputs, with supported schema, requirement, temporal, rule and fixture overlays substituted. Validation compares that manifest to its materialized inputs before running checks. Known generated outputs are excluded; additional source owners and non-ontology application inputs still need explicit inclusion before publication. Existing version 1–3 workspaces retain their original digests and receipts for recovery; create a new workspace to edit requirement links and temporal policies.

For versions 3 and 4, semantic writes and source-grounded inspection require the local authoring adapter and schema parser to match the workspace's pinned manifest. If either is missing or differs, those operations stop with a compatibility error; create a new workspace from the current commit after reviewing the existing draft. This does not automatically migrate draft changes or replace a review.

Version-four workspaces can search the existing requirement register and explicitly link a known class using an expected class-list precondition. The requirement source and schema changes share a revision, digest, receipt and undo; their source patches are shown in review and validation materializes both. A link records an author decision, not proof that the requirement is met, and does not create a requirement or acceptance case.

`ontology_view_suggest` records a bounded, nonbinding concept and perspective suggestion as a workspace event. It does not change the semantic revision or force browser navigation. A connected viewer can choose to focus the suggested concept while the suggestion still refers to the current draft; retries with the same operation ID do not create duplicate events.

The modelling canvas displays the selected concept's bounded information neighbourhood with React Flow and computes initial placement in an ELK web worker. Nodes can be selected with the pointer or keyboard and dragged without changing ontology source; moved positions are kept in the current browser session across reloads. Existing positions are retained when live revisions arrive. The adjacent relationship list remains available as a keyboard-accessible alternative. This is a neighbourhood view, not yet a complete whole-model canvas or a semantic merge editor.

New version-four workspaces can also set an explicit class temporal policy using the expected prior value as a precondition. The policy source shares the same transaction, identity, undo and validation materialization as the schema and requirement register. Selecting a policy does not configure all temporal relationships or establish time-behavior acceptance; those checks and any needed fixtures remain separate. Older version-four workspaces created without the temporal source must be recreated to edit it.

Responsibility perspective labels are stored in `model/responsibility-bindings.json`. `viewpoint.binding_add` can map an existing declared object relationship to a label and category; it cannot create the relationship itself. The mapping source is included in the workspace revision, digest, diff and undo. New workspaces import it from the baseline; older workspaces without that source show the service's fallback mappings and must be recreated to edit mappings. The mapping is deliberately partial and is presentation metadata, not evidence of business completeness.

Cancellation is cooperative: the running fixed check is allowed to finish, then the job stops before the next check and is marked `cancelled`. A cancelling job continues to occupy the workspace validation slot. Cancellation does not promise immediate termination of a running child process.
